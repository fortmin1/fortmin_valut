# RabbitMQ vs RocketMQ
**RocketMQ：业务复杂、高吞吐、需要事务消息 / 延迟消息、Java 微服务、消息容易堆积**
**RabbitMQ：多语言、多协议、复杂灵活路由、中小流量、IoT、通知类异步任务**
## 一、核心维度对比表

|对比项|RabbitMQ|RocketMQ(Apache)|
|---|---|---|
|开发语言|Erlang|Java|
|单机吞吐|1 万～3 万 TPS|5 万～10 万 + TPS，扩展性更强|
|消息堆积能力|一般，大量堆积容易性能下滑|极强，基于磁盘顺序写，支持 TB 级堆积|
|路由模型|Exchange（Direct/Topic/Fanout/Headers），**路由极度灵活**|Topic + Tag，路由能力简单直接|
|事务消息|**无原生支持**，只能使用 Publisher Confirm，分布式事务需要自行实现 Outbox 模式|**原生事务消息**（半消息机制），电商 / 支付核心场景刚需|
|延迟 / 定时消息|依赖插件 TTL+DLX 实现，能力有限、精度差|原生支持；5.0 支持任意时间延迟|
|顺序消息|单队列内有序；全局有序实现复杂|分区有序，易于实现业务顺序（订单流程）|
|协议支持|AMQP、MQTT、STOMP、HTTP，**多协议友好**|私有 TCP 为主；5.0 兼容 AMQP/MQTT，生态弱于 Rabbit|
|运维与监控|自带 Web 管理界面，开箱即用|管控平台相对单薄，通常需要部署 Dashboard|
|集群架构|镜像队列，集群同步成本高，横向扩展一般|NameServer 轻量注册中心，主从 / Dledger 集群，扩容友好|
|技术栈适配|全语言客户端，Python/PHP/Go/Node 友好|Java 生态最强（Spring Cloud Alibaba），其他语言 SDK 成熟度略弱|
|典型短板|大流量堆积容易卡顿；Erlang 人才少，底层调优难|路由模型简单，不适合复杂消息分发|

## 二、什么时候优先选 RabbitMQ

✅ 推荐场景

1. **多语言异构系统**：团队大量使用 Python、PHP、Node、Go 等非 Java 语言
2. **IoT 设备接入**：需要 MQTT 协议接入物联网终端
3. **复杂消息路由场景**：消息需要根据 header、routing-key 做多层分发、多队列绑定
4. **中小规模异步任务**：短信、邮件推送、通知、简单任务队列，流量平稳，峰值不高
5. **需要标准 AMQP 协议，希望能够对接各类第三方中间件**

❌ 不适合

- 消息经常大规模堆积（消费者长时间故障）
- 核心交易链路，需要分布式事务消息
- 单机持续高吞吐（几万 TPS 以上）

## 三、什么时候优先选 RocketMQ

✅ 推荐场景

1. **电商、支付、订单核心业务**：需要**事务消息、订单超时取消（延迟消息）、顺序消息**
2. **Java 技术栈微服务，Spring Cloud Alibaba 体系**
3. **流量波动大、容易消息堆积**（促销峰值、下游服务不稳定）
4. **大规模分布式系统，集群需要水平扩容**
5. 需要消息回溯、批量消费、消息标签过滤等企业级特性

❌ 不适合

- 重度依赖复杂多级路由、基于消息内容动态分发
- 大量 IoT 设备，强依赖原生 MQTT 标准协议
- 技术栈以 PHP/Python 为主，缺少 Java 开发人员

## 四、快速决策 Checklist（直接对照）

1. **是否需要分布式事务消息？** 需要 → **RocketMQ**（RabbitMQ 无解，只能数据库兜底方案）
2. **是否大量 IoT 设备、需要 MQTT 标准协议、多语言客户端？** 是 → **RabbitMQ**
3. **消息峰值高、下游容易故障、经常出现消息堆积？** 是 → **RocketMQ**
4. **是否需要灵活的多级路由、按消息属性动态分发？** 是 → **RabbitMQ**
5. **技术栈以 Java 为主、微服务体系 Spring Cloud Alibaba？** 是 → **优先 RocketMQ**
6. **业务只是简单解耦，流量不大，只是异步通知？** 两者均可：团队熟悉哪个选哪个
